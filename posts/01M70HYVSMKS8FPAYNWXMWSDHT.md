**이 글의 핵심 3줄**
- RISC-V 특권 모드는 U(00)·S(01)·M(11) 셋이고 M만 필수다. QEMU에서 각 모드로 내려가 `ecall`을 실행하자 `mcause`가 M 11, S 9, U 8로 나왔고, 구성에서 S·U를 빼면 `mstatus.MPP`에 쓴 모드가 읽히지 않았다(M·U 구성에서 1을 쓰면 0, M만 있으면 항상 3).
- CSR 12비트 주소는 위 4비트가 규칙이다. [11:10]=11이면 읽기 전용, [9:8]이 접근에 필요한 최소 특권이다. 명세 표로 4,096개 주소를 세면 표준 3,184, 사용자 정의 896, 디버그 모드 전용 16개이고, 이 규칙으로 QEMU의 읽기·쓰기 결과 85칸 중 존재하는 CSR 67칸을 모두 맞혔다.
- WARL 필드는 예외 없이 "읽으면 합법 값"만 보장한다. QEMU에서 `mtvec.MODE` 2·3을 쓰면 쓰기 전체가 무시됐고, `satp.MODE`는 0·8·9·10만 받았고, `misa`는 기본 설정에서 쓰기를 전부 무시했다.
:::

앞 편들에서 비특권 ISA와 코어 구현을 지나왔다. 23편부터는 3부, 특권 아키텍처다. 코어가 응용 프로그램 하나만 돌리는 데서 끝나지 않고 운영체제와 인터럽트, 가상 메모리까지 받치려면 "지금 어느 권한으로 실행 중인가"와 "그 권한이 만질 수 있는 상태가 무엇인가"를 하드웨어가 알아야 한다. 이 두 질문의 답이 특권 모드와 CSR이다. [12편](post:01M6K7VS05ZSDFEQQ7GZW0C1RJ)에서 CSR을 읽고 쓰는 명령어 6개를 봤으니, 이 글은 CSR 쪽에서 무엇이 있고 주소가 어떻게 배치됐는지, 쓴 값이 그대로 읽히지 않는 필드가 무엇인지를 본다. 다음 24편은 이 규칙을 하드웨어 CSR 파일로 만드는 법, 25편은 트랩이다. 이 글에서 `mcause`는 "예외가 났다"는 증거로 숫자만 적고, 트랩 처리의 내용은 25편으로 미룬다.

실습은 QEMU 11.1.3 `virt` 보드(맥 M1 Max)와 `riscv64-elf-gcc` 16.2로 했다. 명세는 특권 명세 20240411판이다.

## 1. 특권 모드: 왜 셋이고, 몇 개를 구현하나

하트(hart, 하드웨어 스레드)는 언제나 특권 수준 하나에서 돈다. 명세 1.2절은 수준 셋을 정의한다.

| 인코딩 | 이름 | 약자 | 주 쓰임 |
|---|---|---|---|
| `00` | User/Application | U | 응용 프로그램 |
| `01` | Supervisor | S | 운영체제 커널 |
| `10` | (예약) | | |
| `11` | Machine | M | 펌웨어, 신뢰하는 코드 |

M은 모든 구현이 가져야 하는 유일한 모드다. 가장 단순한 코어는 M만 가져도 되고(작은 임베디드), M+U(보안이 필요한 임베디드), M+S+U(유닉스 계열 OS)의 세 가지 조합이 명세에 있다. 모드가 높을수록 접근할 수 있는 것이 많고, "한 수준의 CSR과 명령어는 그보다 높은 모든 수준에서도 쓸 수 있다"가 기본 규칙이다. 허용되지 않은 동작을 하면 예외가 난다.

![특권 모드는 M(11)·S(01)·U(00)이고, QEMU에서 각 모드에서 ecall을 실행하면 mcause는 M 11, S 9, U 8이었다. 트랩·ecall은 권한을 올리고 mret·sret은 내린다|full](/img/01M70HYVSMKS8FPAYNWXMWSDHT/c63ea96eb7a7.webp)

모드 사이 이동은 두 방향뿐이다. 낮은 곳에서 높은 곳으로는 **트랩**(예외·인터럽트·`ecall`)으로 가고, 되돌아올 때는 `mret`·`sret`을 쓴다. 명세는 권한이 올라가는 트랩을 vertical, 같은 수준에 머무는 트랩을 horizontal이라 부른다. 어떤 트랩이 어느 모드로 가는지(위임)는 26편, 처리 순서는 25편에서 다룬다.

### 직접 확인: 지금 어느 모드인가

"현재 모드"를 읽는 CSR은 없다. 명세가 일부러 그렇게 만들었다. 하위 모드가 자기 모드를 알 필요가 없고, 가상화 계층이 숨길 수 있게 하려는 뜻이다. 대신 `ecall`의 원인 코드가 모드마다 달라서 사실상 모드 표시가 된다(특권 명세 3.1.15절 표). QEMU에서 M모드와, `mret`으로 내려간 S·U모드에서 각각 `ecall`을 실행하고 `mcause`를 적었다.

| 실행한 모드 | `mcause` | 이름 |
|---|---|---|
| U | 8 | U모드 환경 호출 |
| S | 9 | S모드 환경 호출 |
| M | 11 | M모드 환경 호출 |

RV64와 RV32의 값이 같았다. 구성에서 S를 빼면(M+U) U는 8로 같았고, S가 없으니 S 줄은 없다.

## 2. mstatus.MPP: 구현한 모드는 써 보면 안다

트랩을 받을 때 하드웨어는 "트랩 직전 모드"를 `mstatus`의 `MPP`(비트 12:11, 2비트)에 넣고, `mret`이 그 값으로 돌아간다. 이 필드는 WARL이라 구현한 모드만 담을 수 있다. 명세 3.1.6절은 "M모드 소프트웨어는 모드를 MPP에 쓰고 읽어 그 모드가 구현됐는지 알 수 있다"고 적었다. 세 가지 구성으로 확인했다. 아래 칸은 MPP에 쓴 값(위)과 읽은 값이다.

| 쓴 값 | M+S+U | M+U | M만 |
|---|---|---|---|
| 0 (U) | 0 | 0 | 3 |
| 1 (S) | 1 | 0 | 3 |
| 2 (예약) | 0 | 0 | 3 |
| 3 (M) | 3 | 3 | 3 |

M+U 구성에서 1(S)을 쓰면 0(U)이 읽혔고, M만 있는 구성에서는 무엇을 써도 3이 읽혔다. 구현하지 않은 모드 대신 구현한 모드 중 하나가 남는 셈이다(어느 값이 남을지는 구현 선택). 2는 예약이라 어느 구성에서도 남지 않았다(쓰기 전 값 0이 읽혔다).

M모드 코드가 낮은 모드로 내려가는 방법은 세 줄이다. `mepc`에 갈 주소를, `MPP`에 갈 모드를 쓰고 `mret`을 한다. 실습의 `enter_mode`가 정확히 이 순서다.

```asm
enter_mode:             # a0 = 0(U) 또는 1(S), a1 = 실행할 함수
    csrw mepc, a1       # 돌아갈 주소
    li   t1, 0x1800
    csrc mstatus, t1    # MPP 두 비트를 지우고
    slli a0, a0, 11
    csrs mstatus, a0    # 가려는 모드를 넣고
    mret                # 그 모드로 점프
```

### 모두 1, 모두 0을 쓴 mstatus

`mstatus` 전체에 모두 1을 써서 읽고, 모두 0을 써서 읽었다(끝에 원래 값으로 복원).

| 쓴 값 | RV64 읽은 값 | RV32 읽은 값 |
|---|---|---|
| 모두 1 | `0x8000000a007e79aa` | `0x807e79aa` |
| 모두 0 | `0x0000000a00000000` | `0x00000000` |

RV64의 모두 1 결과를 필드로 풀면(명세 3.1.6절 필드 위치), `SIE`·`MIE`·`SPIE`·`MPIE`·`SPP`·`MPRV`·`SUM`·`MXR`·`TVM`·`TW`·`TSR`이 1이고 `MPP`=3, `FS`=3이다. `UBE`·`MBE`·`SBE`·`VS`·`XS`는 0으로 남았다(QEMU의 이 CPU는 V 확장과 빅엔디언이 없다). 최상위 `SD`(비트 63)는 쓰지 않았는데 1이다. `FS`나 `XS`가 더티(dirty)이면 1이 되는 읽기 전용 요약 비트이기 때문이다. WPRI인 비트 0·2·4와 62:38 등은 읽기 전용 0이었다. 모두 0을 써도 `0xa00000000`이 남는다. 비트 33과 35, 곧 `UXL`=2·`SXL`=2(둘 다 64비트)는 WARL이고 0(예약)을 담을 수 없어 합법 값 2를 유지한 것이다. RV32에는 이 필드가 없어서 0으로 돌아간다.

## 3. CSR 주소 규칙

CSR 주소는 12비트(`csr[11:0]`)로 4,096개가 있다. 명세 2.1절의 규칙은 위 4비트가 접근 권한의 **기본값**이라는 것이다.

![CSR 주소 비트 11:10이 11이면 읽기 전용이고 9:8이 최소 특권이다. 예로 든 CSR 넷의 M·S·U 읽기 결과가 이 규칙대로였고, cycle만 mcounteren=0이라 S·U에서 막혔다|full](/img/01M70HYVSMKS8FPAYNWXMWSDHT/b93d5629ed64.webp)

- `csr[11:10]`: `00`·`01`·`10`이면 읽기·쓰기, `11`이면 읽기 전용.
- `csr[9:8]`: 접근에 필요한 최소 특권. `00` U, `01` S, `10` 하이퍼바이저(H 확장의 HS·VS용), `11` M.
- 나머지 `csr[7:4]` 등: 같은 구역 안의 번호. 표준용과 사용자 정의(custom)용도 이 비트로 나눈다.

이 배치 덕에 권한 검사가 비교기 하나로 끝난다. 명령어의 CSR 주소 칸 `[9:8]`과 현재 모드를 비교하고, 쓰기를 시도하면 `[11:10]`==`11`인지만 보면 된다. 명세 주석도 오류 검사를 단순하게 하고 주소 공간을 크게 쓰려는 선택이라고 설명한다. 12편에서 본 "CSR에 쓰기를 시도하는지는 레지스터 값이 아니라 명령어 칸으로 정한다"와 함께, 쓰기 여부와 권한을 읽기 전에 디코드 단계에서 정할 수 있다.

### 주소 4,096개를 세어 보면

명세의 CSR 주소 구역 표를 그대로 옮겨 Python으로 4,096개를 구역별로 셌다. 수준마다 1,024개씩이다.

| 수준 ([9:8]) | 표준 읽기·쓰기 | 표준 읽기 전용 | 사용자 정의 |
|---|---|---|---|
| U (00) | 512 | 192 | 320 |
| S (01) | 640 | 192 | 192 |
| H (10) | 640 | 192 | 192 |
| M (11) | 624 (+디버그 전용 16) | 192 | 192 |

전체로는 표준 3,184개(읽기 전용 768개 포함), 사용자 정의 896개, 디버그 모드 전용 16개(`0x7B0`~`0x7BF`)다. 사용자 정의 구역은 "미래의 표준 확장이 건드리지 않는다"고 약속된 주소라서, 벤더가 자기 CSR을 넣을 곳이다. M모드의 `0x7A0`~`0x7AF`는 디버그 시스템용이고 `0x7B0`~`0x7BF`는 디버그 모드에서만 보인다(M모드에서 접근하면 불법 명령어여야 한다). 주의할 점 하나: 20240411판의 표는 `0xE00`~`0xEBF`와 `0xF00`~`0xFBF`를 "read/write"라고 적었지만 [11:10]=11은 읽기 전용이라는 본문 규칙과 `mvendorid` 등이 MRO로 적힌 점을 따라 이 글은 읽기 전용으로 셌다(표의 오기로 보인다, 추정).

### QEMU로 대조: 주소 비트만으로 예측

기준 모델은 두 줄이다. "모드 ≥ [9:8]이면 읽을 수 있다", "읽을 수 있고 [11:10]≠11이면 읽은 값 그대로 쓸 수 있다". CSR 18개를 M·S·U 세 모드에서 `csrr`로 읽고, 읽혔으면 같은 값을 `csrw`로 써 보고 `mcause`를 적었다. S·U 모드는 PMP 한 칸(전체 허용)을 열어 두고 `mret`으로 내려가 실행했다.

```c
#define T(n, a) { ul v_ = 0; trap_cause = 0; \
  __asm__ volatile("csrr %0, " a : "=r"(v_)); \
  ul rc_ = cause_take(), wc_ = 0xff; \
  if (!rc_) { __asm__ volatile("csrw " a ", %0" :: "r"(v_)); \
              wc_ = cause_take(); } \
  emit(..., n, rc_, wc_); }
CSRS(T)     /* X("cycle","cycle") X("mstatus","mstatus") ... */
```

| 비교 | RV64 | RV32 |
|---|---|---|
| 시험한 칸 (읽기·쓰기) | 85 | 85 |
| 모델과 일치 | 67 | 67 |
| 모델과 다르고 이유가 있는 칸 | 18 | 18 |
| 이유 없이 다른 칸 | 0 | 0 |

다른 18칸은 두 이유뿐이다. (1) 없는 CSR 12칸: 사용자 정의 주소 `0x8FF`(U 수준)·`0x5C0`(S)·`0x7C0`(M)은 QEMU에 없어서 M모드에서도 불법이었다. 명세 2.1절은 "없는 CSR 접근은 예약", 곧 불법이다. (2) 카운터 6칸: `cycle`·`time`·`instret`은 주소로는 U가 읽을 수 있지만 `mcounteren`이 0(reset 값)이라 S·U에서 불법이었다. 주소 규칙은 기본값일 뿐 CSR이 더 막을 수 있다는 뜻이다. 카운터 허용 비트로 이것을 확인했다.

| `mcounteren`.CY | `scounteren`.CY | S에서 `rdcycle` | U에서 `rdcycle` |
|---|---|---|---|
| 0 | 0 | 불법 | 불법 |
| 0 | 1 | 불법 | 불법 |
| 1 | 0 | 읽힘 | 불법 |
| 1 | 1 | 읽힘 | 읽힘 |

U모드가 읽으려면 M과 S의 허용 비트가 모두 켜져 있어야 했다. 카운터의 이 구조는 24편에서 설계로 다룬다. 낮은 모드에서 특권 명령어를 실행해도 같은 불법 명령어였다. U모드의 `mret`·`sret`·`sfence.vma`와 S모드의 `mret`이 모두 `mcause`=2였다. 명세는 "특권 명령어 위반"과 "불법 명령어"를 구분하지 않는다고 적었다(3.1.15절 주석).

## 4. WARL·WLRL·WPRI: 필드 규칙 셋

CSR 필드마다 쓰고 읽을 때 규칙이 있다(명세 2.3절). 비트 패턴이 모두 의미 있지 않아서다.

| 약자 | 이름 | 쓰기 | 읽기 |
|---|---|---|---|
| WPRI | Reserved Writes Preserve, Reads Ignore | 다른 필드 쓸 때 값을 보존 | 소프트웨어가 무시. 없으면 읽기 전용 0 |
| WLRL | Write/Read Only Legal | 합법 값만 써야 함 | 마지막 쓰기가 합법일 때만 보장 |
| WARL | Write Any, Read Legal | 아무 값이나 가능, 예외 없음 | 언제나 합법 값 |

WPRI는 미래 확장을 위한 빈칸이다. 구현은 읽기 전용 0으로 두고, 소프트웨어는 읽은 값을 보존해서 다시 쓴다. WLRL은 불법 값을 쓰면 읽기가 아무 값(쓴 값과 이전 값에서 결정적으로 정해진)일 수 있고, 예외를 내도 된다. `mcause`의 예외 코드가 WLRL이다. WARL이 가장 많다. 예외 없이 받되 읽으면 합법 값이라, 소프트웨어는 **쓰고 읽어서** 지원 범위를 알아낸다(탐지). 불법 값을 썼을 때 무엇을 남길지는 "쓴 값과 하트 상태에서 결정적으로" 정해지기만 하면 구현의 자유다. 이 자유가 하드웨어 설계자에게는 선택지, 검증하는 사람에게는 구현마다 다른 값이다.

![쓴 값과 읽은 값: mstatus.MPP 2는 무시, mtvec.MODE 2·3은 쓰기 전체 무시, satp.MODE는 0·8·9·10만 수용, misa는 기본 설정에서 전부 무시되고 쓰기를 열면 C·H·M만 지워졌다|full](/img/01M70HYVSMKS8FPAYNWXMWSDHT/f7bd615e4083.webp)

WARL 시험은 쓰고, 읽고, 원래 값으로 복원하는 매크로 하나로 했다.

```c
#define WARL(kind, name, csr, val) do { ul o_ = RD(csr), r_, w_ = (ul)(val); \
  __asm__ volatile("csrw " csr ", %1\n\tcsrr %0, " csr \
                   : "=&r"(r_) : "r"(w_)); \
  WR(csr, o_); emit(kind, name, w_, r_); } while (0)
```

### mtvec: 쓰기 전체를 무시

`mtvec`의 아래 2비트 MODE는 0(직접)과 1(벡터)만 정의되고 ≥2는 예약이다(명세 3.1.7절). 베이스 `0x80004000`에 MODE를 붙여 썼다.

| 쓴 값 | 읽은 값 |
|---|---|
| `0x80004000` (MODE 0) | `0x80004000` |
| `0x80004001` (MODE 1) | `0x80004001` |
| `0x80004002` (MODE 2) | 옛 값 |
| `0x80004003` (MODE 3) | 옛 값 |
| `0x8000407c` | `0x8000407c` |
| 모두 1 | 옛 값 (MODE=3 포함) |

MODE만이 아니라 쓰기 전체가 사라졌다. BASE 쪽까지 옛 값이 남는다는 뜻이다. 명세는 "읽으면 합법 값"만 요구하므로 BASE를 새 값으로 두고 MODE만 되돌리는 구현도 허용된다. 이 선택은 24편에서 구현할 때 고른다. 이 시험의 옛 값은 시작 코드가 쓴 트랩 처리기 주소(`0x80000040`)다.

### satp.MODE와 misa

`satp`(주소 변환, 4장)의 MODE는 4비트다. 명세는 "지원하지 않는 MODE를 쓰면 쓰기 전체가 효과 없다"고 적었다. RV64에서 MODE 0~15에 PPN `0x80000`을 붙여 썼더니 0(Bare), 8(Sv39), 9(Sv48), 10(Sv57)만 읽혔고, 나머지 12개는 옛 값 0이 남았다. RV32는 MODE가 비트 31 하나라 0과 1(Sv32)을 모두 받았다. 지원하는 MODE를 알아내는 방법이 곧 이 "써 보고 읽기"다.

`misa`(3.1.1절)는 WARL이고 `MXL`(최상위 2비트)이 폭을 알려 주며, 아래 26비트가 확장 A~Z다. QEMU에서 읽은 값은 다음과 같다.

| 항목 | RV64 | RV32 |
|---|---|---|
| `misa` | `0x80000000001411ad` | `0x401411ad` |
| MXL | 2 (XLEN 64) | 1 (XLEN 32) |
| 켜진 확장 | A C D F H I M S U | A C D F H I M S U |

`misa`에 모두 0, 모두 1, 비트 하나 지우기, 없는 비트 켜기를 쓰면 QEMU 기본 설정에서는 읽은 값이 항상 원래 값이었다. 명세는 `misa`가 읽기 전용이어도 된다고 허용하므로 맞다(읽기 전용 값을 가져도 WARL). QEMU에 `x-misa-w=true`를 주면 쓰기가 열리는데, 켜진 9개 중 `C`·`H`·`M` 셋만 지워졌고, `A`·`D`·`F`·`I`·`S`·`U`를 지우는 쓰기와 꺼진 비트를 켜는 쓰기는 모두 무시됐다. 명세는 `F`=0, `D`=1이면 둘 다 꺼진다고 하는데, QEMU는 `F`를 지우는 쓰기 자체를 받지 않아 이 규칙은 시험하지 못했다. 시험 뒤 원래 값으로 복원됐다. `C`를 끄면 명령어 정렬(IALIGN)이 32비트로 늘어날 수 있어서, 다음 명령어가 정렬돼 있지 않으면 쓰기를 취소한다는 규칙도 명세에 있다(21편의 정렬 문제와 같은 뿌리다).

## 5. 식별 CSR

M모드의 정보 CSR 다섯 개는 모두 읽기 전용이고 `0xF11`~`0xF15`에 있다(명세 3.1.2~3.1.5절). QEMU에서 읽은 값이다.

| CSR (주소) | 값 | 뜻 |
|---|---|---|
| `mvendorid` (`0xF11`) | 0 | JEDEC 제조사 ID. 0은 "비상업·미구현" |
| `marchid` (`0xF12`) | `0x2a` | 마이크로아키텍처 ID |
| `mimpid` (`0xF13`) | 0 | 구현 버전 |
| `mhartid` (`0xF14`) | 0 | 하트 번호 (하나는 0이어야 함) |

다섯째 `mconfigptr`(`0xF15`)는 설정 정보 구조체의 주소를 가리키는 CSR이다. QEMU에서는 M모드에서 읽혔고, 읽은 값을 다시 써도 읽기 전용이라 불법 명령어(원인 2)였다.

`marchid`는 `0x2a`(10진수 42)로, 최상위 비트가 0이고 0이 아니므로 명세의 "오픈 소스 프로젝트에 RISC-V 인터내셔널이 배정하는 값" 모양이다. 상업 설계는 최상위 비트가 1이어야 한다. 부팅 코드는 `mhartid`가 0인 하트 하나만 초기화를 이어 가게 한다. 이 레지스터 다섯 개가 "읽을 수는 있어야 하지만 0이어도 된다"는 점이 설계에서 중요하다. 구현 비용을 거의 안 들이고 규격을 지킬 수 있다. 또 reset 직후 값은 RV64에서 `mstatus`가 `0x0000000a00000000`(`UXL`=`SXL`=2)이었고 `mie`·`medeleg`·`mcounteren`·`satp`는 0이었다. 명세가 reset 직후 값으로 정하는 것은 일부(`mstatus.MIE`·`MPRV` 등)뿐이고 나머지 하트 상태는 UNSPECIFIED다(3.4절 Reset). 어떤 값으로 시작할지는 플랫폼과 구현이 정한다.

## 6. 주요 CSR 지도

명세의 CSR 목록 표에서 자주 만나는 CSR만 모았다. 이 시리즈에서 어느 편이 다루는지도 적었다.

| 구역 | CSR (주소) | 편 |
|---|---|---|
| M 정보 | `mvendorid` F11, `marchid` F12, `mimpid` F13, `mhartid` F14, `mconfigptr` F15 | 23 |
| M 설정 | `mstatus` 300, `misa` 301, `medeleg` 302, `mideleg` 303, `mie` 304, `mtvec` 305, `mcounteren` 306 | 23·25·26 |
| M 트랩 처리 | `mscratch` 340, `mepc` 341, `mcause` 342, `mtval` 343, `mip` 344 | 25 |
| M 카운터 | `mcycle` B00, `minstret` B02, `mhpmcounter3`~ B03~, `mcountinhibit` 320 | 24 |
| M 메모리 보호 | `pmpcfg0`~ 3A0~, `pmpaddr0`~ 3B0~ | 29 |
| S 설정·처리 | `sstatus` 100, `sie` 104, `stvec` 105, `scounteren` 106, `sscratch` 140, `sepc` 141, `scause` 142, `stval` 143, `sip` 144 | 26 |
| S 주소 변환 | `satp` 180 | 30·31 |
| 비특권 | `fflags` 001, `frm` 002, `fcsr` 003, `cycle` C00, `time` C01, `instret` C02 | 10·12 |

한 가지 구조가 눈에 띈다. S의 `sstatus`·`sie`·`sip`은 M의 `mstatus`·`mie`·`mip`의 **제한된 보기**다. 같은 비트를 가리키되 S가 볼 수 있는 필드만 보인다(명세 3.1.6절). 카운터 `cycle`은 `mcycle`의 읽기 전용 **그림자**다. 읽기 전용이면서 하위 모드에서도 읽혀야 해서 다른 주소(`0xC00`)에 따로 둔 것이고, 명세는 이런 그림자가 현재는 카운터뿐이라고 적었다. 이 둘이 CSR 파일 설계에서 "한 레지스터 상태를 여러 주소가 본다"는 요구가 된다(24편).

## 7. 설계 체크리스트: 특권 모드와 CSR

| 항목 | 규칙 |
|---|---|
| 필수 모드 | M만 필수. 1·2·3개 조합(M, M+U, M+S+U) |
| 모드 표시 | 현재 모드를 읽는 CSR은 없음. 내부 2비트는 구현이 가진다 |
| `MPP` | WARL. 구현한 모드만 담는다. 예약 2는 담지 않음 |
| 주소 검사 | 현재 모드 ≥ `csr[9:8]` 아니면 불법. 쓰기 시도에 `csr[11:10]`==11이면 불법 |
| 없는 CSR | 읽기·쓰기 모두 불법 명령어 |
| 추가 차단 | 카운터는 `mcounteren`·`scounteren`이 주소 규칙 위에 더한다 |
| WARL 불법 값 | 예외 금지. 읽으면 합법 값. 쓴 값에서 결정적으로 |
| WLRL 불법 값 | 예외를 내도 되고, 읽은 값은 결정적이면 아무 값 |
| WPRI | 구현하지 않으면 읽기 전용 0. 소프트웨어가 보존 |
| 다중 필드 WARL | 한 CSR이 다른 CSR의 합법 값 범위를 바꾸면 그 필드는 새 범위 안의 UNSPECIFIED 값(2.4절) |
| `misa` | 읽기 전용 0도, 읽기 전용 값도 허용. 쓰기로 `C`를 끄면 정렬 규칙 확인 |
| 식별 5개 | 읽혀야 하지만 0 가능. `mhartid` 하나는 0 |
| 그림자·보기 | `sstatus`는 `mstatus`의 일부 보기, `cycle`은 `mcycle` 그림자 |
| 특권 명령어 위반 | `mret`·`sret`·`sfence.vma`는 낮은 모드에서 불법 명령어(원인 2) |

## 정리

- 특권 모드는 U·S·M 셋이고 M만 필수다. QEMU에서 각 모드의 `ecall`은 `mcause` 8·9·11을 남겼고, 모드를 구현했는지는 `MPP`에 써 보고 읽어서 알 수 있었다.
- CSR 주소의 `[11:10]`이 읽기 전용, `[9:8]`이 최소 특권이라는 규칙으로 QEMU의 존재하는 CSR 67칸을 모두 맞혔다. 없는 CSR 12칸과 카운터 허용 비트 6칸만 규칙 밖이었다.
- WARL 필드는 예외 없이 합법 값을 읽게 하고 무엇을 남길지는 구현이 정한다. QEMU는 `mtvec.MODE` 2·3과 지원하지 않는 `satp.MODE`에서 쓰기 전체를 무시했다.
- 식별 CSR은 읽혀야 하지만 0이어도 된다. `sstatus`와 `cycle`처럼 한 상태를 여러 주소가 보는 구조가 CSR 파일 설계의 요구가 된다.

**다음 글:** 24편은 CSR 파일을 하드웨어로 만든다. 읽기·쓰기에 부작용이 있는 CSR을 어떻게 처리하는지, 위 주소 규칙으로 권한 검사 회로를 어떻게 짜는지, 카운터와 `mcountinhibit`이 어떻게 맞물리는지를 본다.
