**이 글의 핵심 3줄**
- CSR 파일은 "주소 디코드와 권한 검사 → 읽기 mux, 쓰기값 계산 → WARL 정리 → 저장소" 한 줄기다. 쓰기를 시도하는지는 값이 아니라 명령어 칸(`rs1`이 `x0`인가)으로 정해야 한다. 읽기 전용 `mhartid`에 `csrrs rd, mhartid, t0`(t0=0)을 하면 QEMU도 불법 명령어를 냈고, `rs1=x0`·`uimm=0`일 때만 읽혔다.
- 이 규칙을 사이클 단위 파이썬 모델로 만들어 QEMU(RV64 349칸, RV32 351칸)와 대조했다. 권한 행렬, 보기(`sstatus`·`sie`), WARL 정리는 모두 맞았다. 카운터만 어긋났다. 명세 순서 모델은 RV64에서 19칸이 1씩 달랐고, "쓰기를 먼저 반영하고 그 명령어도 센다"로 바꾼 모델은 349칸이 모두 맞았다.
- 명세는 `minstret`에 쓴 값이 바로 다음 명령어에서 읽힌다고 하는데, QEMU(`-icount shift=0`)는 1000을 쓰면 1001을 읽혔다. RV32에서는 `mcycle` 아래 32비트가 넘쳐도 `mcycleh`가 오르지 않았다(`mcycle`이 `0xffffffff`를 지나 1이 됐는데 `mcycleh`는 0). 명세 설정의 모델은 같은 순서에서 하위·상위를 따로 읽으면 `0x1ffffffff`가 나온다고 예측한다.

[23편](post:01M70HYVSMKS8FPAYNWXMWSDHT)은 CSR이 무엇이고 주소가 어떻게 배치됐는지, 쓴 값이 그대로 읽히지 않는 필드가 무엇인지를 봤다. 이 글은 그 규칙을 하드웨어로 옮긴다. CSR 명령어 하나가 들어오면 파일 안에서 무슨 일이 일어나는지, 읽기와 쓰기에 딸린 규칙이 회로에서 어디에 붙는지, 카운터와 `mcountinhibit`이 클록마다 어떻게 맞물리는지를 순서대로 본다. 트랩이 실제로 어떻게 들어가고 `mepc`·`mcause`가 어떻게 채워지는지는 25편이다. 이 글에서 `mcause`는 "불법 명령어(원인 2)가 났다"는 증거로만 쓴다.

설계 선택을 눈으로 확인하려고 CSR 파일의 사이클 단위 모델(`csrfile.py`, 193줄)을 만들었다. M+S+U와 F가 있고 H·V는 없는 하트 하나, 명령어당 1사이클이다. 같은 시나리오를 모델과 QEMU 11.1.3 `virt`(맥 M1 Max, `riscv64-elf-gcc` 16.2)에 먹여 항목별로 비교했다. 명세는 비특권·특권 명세 20240411판이다. 방법과 전체 결과는 7절에 있다.

## 1. CSR 파일의 뼈대

![CSR 명령어 하나가 지나는 길. 주소·명령어 칸·현재 모드로 검사하고, 통과하면 읽기 mux와 쓰기값 계산이 같은 저장소를 읽고 쓴다. 검사에서 걸리면 불법 명령어|full](/img/01M75HAZ9MMPAAWKECZKWMQGZ0/bf84c0b99335.webp)

CSR 명령어는 읽고, 고치고, 쓰는 동작을 한 번에 한다(Zicsr, 비특권 명세 7장). 파일 안에서 보면 다음 여섯 부분이다.

| 부분 | 하는 일 |
|---|---|
| 디코드 | `csr[11:0]`로 어느 CSR인지 고른다. 없는 주소를 가려낸다 |
| 검사 | 모드, 읽기 전용 구역, 추가 조건을 보고 불법 여부를 낸다 |
| 읽기 mux | 선택된 CSR의 읽은 값(보기·그림자 포함)을 `rd`로 보낸다 |
| 쓰기값 계산 | `rw`는 `rs1`, `rs`는 읽은 값 OR `rs1`, `rc`는 읽은 값 AND NOT `rs1` |
| WARL 정리 | 합법이 아닌 값을 합법 값으로 바꾸거나 쓰기를 무시한다 |
| 저장소 | 플립플롭. 여러 주소가 같은 저장소를 본다 |

한 가지를 먼저 확인해 두자. 쓰기값 계산이 쓰는 "읽은 값"은 그 주소로 **보이는** 값이다. `csrrs t0, sstatus, t1`은 `mstatus` 전체가 아니라 `sstatus` 보기의 값에 `t1`을 OR한 것을 `sstatus`에 쓴다. 3절에서 이 점이 실제로 중요해진다.

### 읽기를 하는가, 쓰기를 하는가

이 구분은 명령어 칸으로만 정한다. 명세 표(Zicsr)를 줄이면 다음과 같다.

| 명령어 | 읽는가 | 쓰는가 |
|---|---|---|
| `csrrw`·`csrrwi` | `rd`≠`x0`일 때만 | 항상 |
| `csrrs`·`csrrc`(와 i형) | 항상 | `rs1`≠`x0`(`uimm`≠0)일 때만 |

`csrrw x0, ...`는 읽지 않으므로 읽기에 딸린 부작용이 일어나지 않아야 하고, `csrrs rd, csr, x0`은 쓰지 않으므로 쓰기 부작용도, 읽기 전용 CSR에 대한 불법 명령어 예외도 없어야 한다. 이 두 규칙이 `csrr`(=`csrrs rd, csr, x0`)로 읽기 전용 카운터를 읽을 수 있는 이유다. 명세 주석은 표준 CSR에는 읽기 부작용이 없다고 적었다. 그래서 `rd=x0`일 때 읽지 않는 규칙은 지금 표준 CSR에서는 눈에 보이지 않고, 사용자 정의 CSR이나 읽으면 FIFO가 한 칸 나가는 장치를 CSR로 만들 때 의미가 생긴다.

쓰기 쪽에는 눈에 띄는 함정이 하나 있다. `rs1`이 `x0`이 아닌데 값이 0인 경우다. 명세는 이때 필드별 부작용은 일어나지 않지만 CSR 전체를 쓰는 부작용은 일어난다고 적었다. 읽기 전용 CSR이면 불법 명령어다. 쓰기 시도 신호를 "쓸 값이 0이 아닌가"로 만들면 틀린다는 뜻이다. 12편에서 말한 "쓰기 시도는 레지스터 값이 아니라 명령어 칸으로 정한다"가 바로 이것이다.

## 2. 권한 검사 회로

23편의 주소 규칙을 회로로 옮기면 검사는 네 가지다.

1. 존재하는 주소인가. 구현하지 않은 CSR은 읽기·쓰기 모두 불법이다.
2. 모드 ≥ `csr[9:8]`인가. U=00, S=01, M=11이고 10(H 수준)은 H 확장이 없으면 쓰이지 않으므로, 2비트 부호 없는 비교기 하나로 된다.
3. 쓰기 시도이고 `csr[11:10]`=11이면 불법이다.
4. 추가 조건: 카운터 허용 비트(`mcounteren`·`scounteren`), `mstatus.TVM`(S모드의 `satp` 접근), `mstatus.FS`=Off(`fcsr` 계열) 같은 CSR별 조건.

```systemverilog
// 예시(시뮬레이션하지 않았다). priv: U=00, S=01, M=11
wire wr_try  = (funct3[1:0] == 2'b01) | (rs1_f != 5'd0);
wire rd_try  = !(funct3[1:0] == 2'b01 && rd_f == 5'd0);
wire priv_ok = (priv >= csr[9:8]);
wire ro_ok   = !(wr_try && csr[11:10] == 2'b11);
wire illegal = csr_en && !(exists && priv_ok && ro_ok && extra_ok);
```

`funct3[1:0]==01`은 `csrrw`와 `csrrwi`고, `rs1_f`는 `rs1` 칸 5비트다. i형에서는 이 칸이 `uimm`이므로 같은 식이 두 꼴을 모두 맞춘다. 이 신호들은 디코드 단계에서 만들 수 있고, 검사 결과가 "불법"이면 CSR 파일에는 쓰기 허용 신호를 내보내지 않는다. 그래야 불법 명령어가 CSR을 바꾸지 않는다.

### 직접 확인: 권한 행렬

QEMU에서 M·S·U 모드로 같은 CSR 15개를 읽고(`csrrs`, `rs1=x0`) 0을 써 보았다. 먼저 `mcounteren`·`scounteren`이 모두 0인 상태다.

| CSR | M | S | U |
|---|---|---|---|
| `mstatus`, `mscratch`, `mcycle` | 읽기·쓰기 | 불법 | 불법 |
| `sstatus`, `satp`, `sscratch` | 읽기·쓰기 | 읽기·쓰기 | 불법 |
| `cycle`, `instret`, `time`, `hpmcounter3`, `mhartid` | 읽기 | 불법 | 불법 |
| `hpmcounter31`, `0x600`, `0x7c0`, `0x8ff` | 불법 | 불법 | 불법 |

마지막 줄이 존재 검사다. `hpmcounter31`은 이 QEMU가 카운터를 16개(3~18번)만 구현해서, `0x600`(`hstatus`)은 H를 껐으므로, `0x7c0`·`0x8ff`는 사용자 정의 구역이지만 이 하트에 아무것도 없으므로 M모드에서도 불법이다. `cycle`을 M모드에서 읽는 것은 되지만 쓰기는 `csr[11:10]`=11이라 불법이다.

카운터 그림자는 `mcounteren`과 `scounteren`을 더 본다. 설정을 바꿔 가며 같은 읽기를 했다.

| 구성 | `cycle`·`instret` | `time` | `hpmcounter3` |
|---|---|---|---|
| S, `mcounteren`=0 | 불법 | 불법 | 불법 |
| S, `mcounteren`=5 | 읽기 | 불법 | 불법 |
| U, `mcounteren`=5, `scounteren`=0 | 불법 | 불법 | 불법 |
| U, `mcounteren`=5, `scounteren`=7 | 읽기 | 불법 | 불법 |

5는 CY(비트 0)와 IR(비트 2)이다. 마지막 줄에서 `scounteren`=7은 TM(비트 1)도 켜졌는데 `time`이 불법인 것에 주목하자. U모드는 두 레지스터의 비트가 **모두** 켜져 있어야 읽고(명세 4.1.5절 주석), `mcounteren.TM`이 0이었다. 회로로는 `ctr_ok = (priv==M) | (mcounteren[n] & (priv==S | scounteren[n]))`이다.

추가 조건의 다른 예로 `mstatus.TVM`을 켜자(M모드에서 쓰고 S모드로 내려감). S모드의 `satp` 읽기·쓰기는 불법 명령어가 됐고, 같은 S모드에서 `sstatus`는 읽혔다. TVM을 끄면 `satp`가 다시 읽혔다(특권 명세 3.1.6절). 검사에 "CSR별 추가 조건"이 들어가는 자리가 이것이다.

### 직접 확인: `rs1` 칸과 값

읽기 전용인 `mhartid`(0xF14)를 M모드에서 여러 꼴로 건드렸다.

| 명령어 | 결과 |
|---|---|
| `csrr rd, mhartid` (`csrrs`, `rs1=x0`) | 읽힘(0) |
| `csrrs rd, mhartid, t0` (t0=0) | 불법 |
| `csrrc rd, mhartid, t0` (t0=0) | 불법 |
| `csrrs rd, mhartid, t0` (t0=1) | 불법 |
| `csrrsi`·`csrrci rd, mhartid, 0` | 읽힘(0) |
| `csrrsi rd, mhartid, 1` | 불법 |
| `csrw`·`csrrw`·`csrrwi` (값 0) | 불법 |

`t0`이 0이어도 `rs1`이 `x0`이 아니면 쓰기 시도였다. `csrrw`는 값이 0이어도 항상 쓰기라서 읽기 전용이면 불법이다. 모델과 QEMU가 이 줄을 모두 같게 냈다.

## 3. 보기와 그림자: 한 상태를 여러 주소가 본다

![같은 저장소를 다른 주소로 보는 네 가지. sstatus는 mstatus의 S 필드, sie는 mie를 mideleg로 거른 것, cycle은 mcycle의 읽기 전용 그림자, fflags는 fcsr의 낮은 5비트다|full](/img/01M75HAZ9MMPAAWKECZKWMQGZ0/088eceb43be6.webp)

"보기"는 저장소 하나를 마스크로 걸러 보는 주소다. 구현은 두 마스크로 끝난다. 읽을 때는 `저장소 & 읽기 마스크`, 쓸 때는 `저장소 = (저장소 & ~쓰기 마스크) | (쓸 값 & 쓰기 마스크)`다. 보기의 비트를 따로 저장하는 플립플롭은 없다. 따로 저장하면 두 주소의 값이 갈라지는 버그의 길이 열린다.

### `sstatus`는 `mstatus`의 일부다

`mstatus`와 `sstatus`에 −1과 0을 번갈아 쓰고 둘을 읽었다(RV64).

```text
csrw mstatus,0    mstatus 0x0000000a00000000
csrw sstatus,-1   mstatus 0x8000000a000c6122
                  sstatus 0x80000002000c6122
csrw mstatus,-1   mstatus 0x8000000a007e79aa
                  sstatus 0x80000002000c6122
csrw sstatus,0    mstatus 0x0000000a00721888
                  sstatus 0x0000000200000000
```

`sstatus`에 −1을 쓰자 `SIE`·`SPIE`·`SPP`·`FS`·`SUM`·`MXR`만 켜졌고 `MIE`·`MPIE`·`MPP`는 0이었다. `mstatus`에 −1을 쓰면 그 위에 `MIE`·`MPIE`·`MPP`(=3)·`MPRV`·`TVM`·`TW`·`TSR`이 더 켜지는데 `sstatus`는 똑같이 `0x000c6122`다. 마지막으로 `sstatus`에 0을 쓰자 S 필드만 지워지고 `mstatus`에 `0x00721888`(M 필드들)이 남았다. 최상위 `SD`(비트 63)는 읽기 전용 요약 비트다. 구현에서는 저장하지 않고 읽기 경로에서 `FS==3`(또는 `VS`·`XS`가 Dirty)을 보고 만들어 붙이는 것이 간단하다. `sstatus`에서 `FS`를 지우자 `SD`도 같이 지워졌으니 이 구현과 맞는다. `UXL`(비트 33:32)은 `sstatus`에 보이지만 값은 읽기 전용 2이고, `SXL`은 `sstatus`에 보이지 않는다.

`csrrs`·`csrrc`도 보기 위에서 계산한다. `mstatus`를 0으로 만들고 `csrrs sstatus, (SPP|SUM)`을 하자 읽혀 나온 옛 값은 `sstatus`의 `0x200000000`(`UXL`만)이었고 `mstatus`는 `0xa00040100`이 됐다. 이어서 `csrrc sstatus, SPP`를 하자 `0xa00040000`이 됐다.

### `sie`·`sip`는 `mie`·`mip`를 `mideleg`로 거른 것

명세는 이렇게 적었다. 인터럽트가 `mideleg`로 S모드에 위임되면 `sip`에 보이고 `sie`로 마스크할 수 있고, 아니면 `sip`·`sie`의 그 비트는 읽기 전용 0이다(특권 명세 3.1.9절 끝 문단). 20240411판의 4.1.3절 본문은 "`sip`·`sie`는 `mip`·`mie`의 부분집합"이라고만 하니, 위임 조건은 3.1.9절에서 확인해야 한다. 하드웨어로는 AND 게이트 하나다. `sie`의 읽기·쓰기 마스크가 `mideleg & S 인터럽트 비트`다.

QEMU에서 확인한 값이다(M모드에서 접근).

| 단계 | 읽은 값 |
|---|---|
| `mie`에 `0xffff`를 씀 | `mie` = `0xaaa` |
| `mideleg`=0일 때 | `sie` = 0, `sie`에 쓴 뒤에도 `mie` 그대로 |
| `mideleg`에 `0x222`를 씀 | `mideleg` = `0x222`, `sie` = `0x222` |
| `sie`에 0을 씀 | `mie` = `0x888` |
| `sie`에 `0xffff`를 씀 | `mie` = `0xaaa` |

`mie`에 `0xffff`를 쓰면 6개 비트(1·3·5·7·9·11, 곧 SSI·MSI·STI·MTI·SEI·MEI)만 남았다. 구현하지 않은 인터럽트의 `mie` 비트는 읽기 전용 0이어야 한다는 규칙이다. `sie`를 0으로 쓰면 위임된 S 비트(`0x222`)만 지워져 `0x888`이 남았다. `mip`도 비슷하다. M모드에서 `0xaaa`를 쓰자 읽은 값이 `0x2a2`였다. 쓸 수 있는 비트인 SSIP·STIP·SEIP(1·5·9)와, 우리가 쓰지 않았는데 1로 읽힌 비트 7(MTIP)이다. MTIP는 장치가 올리는 입력이라 쓰기와 무관하다(왜 올라와 있는지는 확인하지 않았다). `sip`는 `0x222`로 보였고, `sip`에 0을 쓰자 `mip`가 `0x2a0`이 됐다. S모드가 쓸 수 있는 비트는 SSIP뿐이라서 STIP·SEIP는 그대로다. `sip`에 `0xffff`를 쓰자 SSIP만 다시 켜져 `0x2a2`로 돌아왔다.

`mip`에는 읽기와 쓰기 경로가 다른 비트도 있다. 명세는 SEIP를 읽을 때는 "소프트웨어가 쓴 비트 OR 외부 인터럽트 신호"를 주지만 `csrrs`·`csrrc`의 읽고-고치고-쓰기에는 소프트웨어 비트만 참여한다고 적었다(3.1.9절). 읽기 mux의 입력과 쓰기 계산의 입력이 다르다는 뜻이다. QEMU `virt`에서 외부 신호를 만들지 않아 이 동작은 시험하지 못했다.

`mideleg`를 쓰면 `sie`의 쓰기 가능 여부가 바뀐다. 명세는 별칭 필드가 읽기 전용에서 쓰기 가능으로 바뀌면 그 값이 별칭의 현재 값을 즉시 반영해야 하고 UNSPECIFIED가 아니라고 적었다(2.4절). 보기 방식으로 만들었으면 자동으로 맞다. 따로 저장했다면 `mideleg`를 쓸 때 복사하는 회로가 필요하다.

### `fflags`·`frm`·`fcsr`: 별칭, 그리고 다른 CSR을 바꾸는 쓰기

`fcsr`(0x003)는 8비트이고 `fflags`(0x001)가 `[4:0]`, `frm`(0x002)이 `[7:5]`다. 별칭 둘과 저장소 하나다. 더 흥미로운 것은 `mstatus.FS`와 맺는 관계다. QEMU에서 확인했다.

| 상황 | 결과 |
|---|---|
| `FS`=Off에서 `fcsr`·`fflags` 읽기 | 불법 명령어(원인 2) |
| `FS`=Initial(1)에서 `fflags` 읽기 | 0, `mstatus` 그대로 |
| `fflags`에 `0x1f` 쓰기 | `fcsr`=`0x1f`, `mstatus.FS`=3(Dirty), `SD`=1 |
| `FS`=Clean(2)에서 `frm` 읽기 | 0, `FS` 그대로 2 |
| `frm`에 `0xff` 쓰기 | `frm`=7(3비트만 저장), `fcsr`=`0xff`, `FS`=3 |

FP 상태를 바꾸는 쓰기는 `mstatus.FS`를 Dirty로 만든다. 읽기는 FS를 건드리지 않는다. 이것이 CSR 파일의 쓰기 포트가 두 곳이어야 하는 이유다. `mstatus` 저장소는 `csrw mstatus`와 FP 쓰기(`fcsr`·FP 레지스터 갱신) 양쪽에서 바뀐다. 한 명령어에서 둘이 겹칠 일은 없으니 우선순위가 아니라 병합(OR 같은)으로 만들어도 되지만, 파이프라인에서 서로 다른 명령어가 서로 다른 단에서 쓴다면 문제가 된다(6절).

### `cycle`·`instret`·`time`은 읽기 전용 그림자

`cycle`·`instret`은 `mcycle`·`minstret`의 읽기 전용 그림자고 `time`은 메모리 맵 `mtime`의 그림자다(명세 3.1.11절). 읽기 마스크가 전체이고 쓰기 마스크가 0인 보기에 2절의 허용 비트 검사가 붙은 것이다. `time`은 읽기를 `mtime` 레지스터 읽기로 바꿔 구현해도 되고(명세 주석) 이 글의 모델은 값을 다루지 않는다.

## 4. WARL 정리 회로

23편에서 "mtvec의 MODE를 어떻게 처리할지는 24편에서 고른다"고 했다. 선택지는 세 가지다.

| 방식 | 회로 | 3을 쓰면 |
|---|---|---|
| (가) 쓰기 전체 무시 | 쓰기 허용 = `we & ~wdata[1]` | 옛 값 그대로 |
| (나) MODE[1]만 0으로 | 저장할 때 `wdata[1]`을 0으로 | MODE=1(벡터)이 저장됨 |
| (다) MODE 고정 | 필드를 상수 0(직접 모드) | MODE=0 |

고르는 기준은 소프트웨어가 어떻게 속느냐다. (나)는 MODE=3을 쓰면 1이 남아서 "예약값을 쓰면 벡터 모드가 된다"는 이상한 결과가 나온다. (다)는 벡터 모드를 못 쓴다. 이 글은 (가)를 고른다. BASE와 MODE를 한 번에 쓰는 코드가 불법 MODE를 쓰면 BASE도 함께 바뀌지 않아서, 쓴 값과 읽은 값이 다르다는 사실로 실패를 알 수 있다. QEMU도 (가)였다. M모드의 `mtvec`이 이 시험 중에 바뀌면 트랩 처리기가 깨지므로 같은 규칙인 `stvec`로 확인했다.

| 쓴 값 | 읽은 값 |
|---|---|
| `0x80001000` (MODE 0) | `0x80001000` |
| `0x80002001` (MODE 1) | `0x80002001` |
| `0x80003003` (MODE 3) | `0x80002001` (옛 값) |
| `0x80004002` (MODE 2) | `0x80002001` (옛 값) |

같은 방식으로 정리하는 다른 필드를 QEMU로 확인했다.

| 필드 | 쓴 값 | 읽은 값 |
|---|---|---|
| `mstatus.MPP` (M+S+U) | 1, 2, 3, 2 순서로 | 1, 1, 3, 3 |
| `satp.MODE` (RV64) | 0·1·5·8·9·10·11·15 | 0·8·9·10만 받음 |
| `mcounteren`, `scounteren` | −1 | `0x7ffff` (비트 0~18) |
| `mcountinhibit` | −1 | `0x7fffd` (TM 비트 1 없음) |

`MPP`는 필드 단위로 옛 값을 유지했다. 예약값 2를 쓰면 방금 쓴 1이나 3이 그대로 남는다. 회로로는 `mpp_d = (wdata[12:11]==2'b10) ? mpp_q : wdata[12:11]`다. `satp`는 MODE가 합법이 아니면 쓰기 전체가 무시되어(명세 4.1.11절) `we_satp = we & mode_legal`로 쓴다. RV32에서는 MODE가 비트 31 하나라 0과 1이 모두 받아들여졌다. 카운터 허용 레지스터는 존재하는 카운터(CY, TM, IR, HPM 3~18)만 비트를 가진다. `mcountinhibit`은 TM 비트가 없다. `time`은 `mtime`을 공유할 수 있어 억제할 수 없다는 것이 명세의 이유다(3.1.12절 주석).

여기까지 합법 값으로 만드는 방식은 모두 모델 인자(`mpp`, `tvec`, `satp_modes`)다. 명세가 구현에 맡긴 선택을 코드 한 곳에 드러내 두면 검증 때 어느 쪽을 골랐는지 묻지 않아도 된다.

## 5. 카운터와 `mcountinhibit`

카운터는 64비트이고 `mcycle`은 클록마다, `minstret`은 명령어가 끝날 때마다 오른다. RV32에서는 아래 절반 `mcycle`(0xB00)과 위 절반 `mcycleh`(0xB80)를 따로 읽는다(2.7절). `mcountinhibit`의 CY(비트 0)·IR(비트 2)가 켜지면 해당 카운터가 멈추고, 이 레지스터는 접근 가능 여부에는 영향이 없다(3.1.12절). 회로는 쓰기 허용 신호가 증가를 **대신하게** 만들면 명세와 같다.

```systemverilog
// 예시(시뮬레이션하지 않았다). _q는 이번 사이클 시작 때의 레지스터 값
mcycle_d   = wr_mcycle   ? wdata
           : inhibit_q[0] ? mcycle_q : mcycle_q + 1;
minstret_d = wr_minstret ? wdata
           : inhibit_q[2] ? minstret_q : minstret_q + retire;
```

이렇게 짜면 두 규칙이 저절로 나온다. 쓰는 명령어가 카운터를 쓰면 그 명령어의 증가는 사라진다(`wdata`가 증가를 대신한다). `mcountinhibit`을 쓰는 명령어는 `inhibit_q`(옛 값)을 보므로 그 명령어 자신의 증가는 옛 설정을 따른다. 명세 근거는 Zicsr의 문장("CSR을 쓰면 증가 대신 쓰기가 이뤄진다. 특히 `instret`에 쓴 값은 다음 명령어가 읽는 값이다")과 3.1.10절의 "CSR 쓰기는 쓰는 명령어가 다른 면에서 끝난 뒤에 효력을 낸다"이다. `mcycle`과 `mcountinhibit`에 대한 해석은 이 두 문장에서 끌어낸 것이다.

![mcycle에 1000을 쓴 뒤 읽은 값은 명세 순서에서 1000, 1001, 1003, 1004이고 QEMU에서 1001, 1002, 1004, 1005다. mcountinhibit을 0으로 되돌린 뒤에도 QEMU가 1씩 크다|full](/img/01M75HAZ9MMPAAWKECZKWMQGZ0/050153815f60.webp)

### 직접 확인: 같은 사이클 쓰기와 증가

QEMU는 기본 설정에서 `mcycle`을 호스트 시계로 센다. `mcycle`에 1000을 쓰고 읽는 창을 4번 돌리자 첫 읽기가 3000 또는 4000이었고 읽기 사이 간격도 1이 아니었다(4번 중 한 줄: 4000, 7000, 9000, 12000, 14000). 사이클 정확한 시뮬레이터가 아니라는 뜻이다. `-icount shift=0`을 주면 명령어 하나가 1틱이 되어 값이 결정적이다. 이하는 이 설정이다. 즉 QEMU의 "cycle"은 실행한 명령어 수고 CPI는 1이다.

시험은 M모드에서 `csrw mcycle, s1`(s1=1000) 뒤에 읽기 명령어를 이어 붙이고 중간에 `nop`을 끼운 창이다. 값은 창이 끝난 뒤에 한꺼번에 저장해서 측정 코드가 사이에 끼어들지 않는다.

| 읽은 값 (순서대로) | `mcycle` 창 | `minstret` 창 |
|---|---|---|
| 명세 순서 모델 | 1000, 1001, 1003, 1004 | 1000, 1001, 1003, 1004 |
| QEMU | 1001, 1002, 1004, 1005 | 1001, 1002, 1004, 1005 |

`minstret`에 1000을 쓰고 바로 다음 명령어가 읽은 값은 명세가 1000, QEMU가 1001이었다. 쓰는 명령어도 퇴직한 명령어인데 명세는 그 증가를 쓴 값이 대신한다고 하므로, 명세대로라면 `csrw minstret`는 `minstret`에 한 번도 세어지지 않는다. QEMU는 쓰기를 먼저 반영한 뒤 그 명령어도 세는 것으로 보인다(추정: 쓴 시점의 명령어 수를 기준점으로 삼는 계산 방식). `mcountinhibit`도 같은 순서다. CY·IR을 5로 쓴 직후 `mcycle`은 1002, `minstret`은 1001로 멈췄고(`nop` 뒤에도 같음) 이 값은 두 순서가 일치했다. 하지만 0으로 되돌린 뒤에는 명세 순서가 1002, 1002, 1004를, QEMU가 1003, 1003, 1005를 냈다. 명세 순서에서는 되돌리는 명령어가 옛 설정(억제)을 따라 세어지지 않고, QEMU는 새 설정(허용)을 먼저 적용해 그 명령어도 센다.

CY만 억제하면(QEMU 값) `mcycle`은 1002에서 멈추는 동안 `minstret`은 1003에서 1005로 계속 올랐다. 두 카운터의 억제 비트가 독립이라는 뜻이다. `csrrs`로 달리는 카운터를 고치는 경우도 눈여겨보자. `mcycle`에 1000을 쓰고 `csrrs rd, mcycle, (1<<20)`을 한 뒤 두 번 읽었다. 명세 순서는 읽은 옛 값 1000, 그 뒤 `0x1003e8`, `0x1003e9`(1000과 2^20을 OR한 값에서 이어 감)였고 QEMU는 1001, `0x1003ea`, `0x1003eb`였다. 읽고-고치고-쓰는 명령어가 달리는 카운터에 쓰면 그 사이클은 증가하지 않고 사라진다. 카운터를 실시간으로 보정하려는 소프트웨어가 알아야 할 점이다.

### 하드웨어 성능 카운터

`mhpmcounter3`~18은 16개가 구현됐고 `hpmcounter31`은 불법이었다. `mhpmcounter3`에 1000을 쓰면 1000이 읽혔고 몇 명령어 뒤에도 1000이었다. `mhpmevent3`에 7을 쓰면 7이 읽혔다. `mhpmcounter3`이 계속 1000인 것은 이 QEMU가 7번 이벤트를 세지 않는 것으로 보인다(추정). 명세는 모든 카운터를 구현하는 것을 권하지만 카운터와 이벤트 선택기를 모두 읽기 전용 0으로 두는 것도 합법이라고 한다(3.1.10절). 코어를 작게 만든다면 이쪽이 가장 싸다. 이때 `mcounteren`·`mcountinhibit`의 해당 비트도 읽기 전용 0으로 둔다.

### RV32: 반쪽 두 번 읽기

RV32에서 64비트 카운터를 두 번에 읽으면 사이에 올림이 끼어든다. 비특권 명세 8장이 `rdcycleh`, `rdcycle`, `rdcycleh`를 읽고 위 절반이 같을 때까지 되풀이하는 코드를 주는 이유다. 명세 설정(올림 있음, 쓰기가 증가를 대신함)의 모델에서 `mcycleh`=0, `mcycle`=`0xfffffffd`를 쓰고 (하위, 상위, 하위, 상위) 순서로 읽자 `fffffffd, 0` 다음에 `ffffffff, 1`이 나왔다. 두 번째 쌍은 하위를 올림 전에, 상위를 올림 뒤에 읽은 찢어진 값 `0x1ffffffff`다. 실제 값은 `0x100000000` 근처다. 이것은 모델의 예측이다.

QEMU에서는 재현되지 않았다. `mcycle`에 `0xfffffffe`를 쓰고 읽자 하위가 `ffffffff`, 다음 읽기에서 `1`, 또 `3`으로 갔는데 `mcycleh`와 `cycleh`는 계속 0이었다. 64비트 카운터라면 `mcycleh`가 1이 되어야 한다. QEMU RV32(11.1.3, `-icount shift=0`)가 하위 32비트의 올림을 위 절반에 전하지 않는 것으로 보인다(추정). 모델의 `carry='none'` 인자가 이 동작이다. 명세와 어긋나는 QEMU 동작은 이것과 위의 쓰기 순서 두 가지였고, 둘 다 카운터 한정이다.

## 6. 파이프라인 안의 CSR

[17편](post:01M6K8E2MPEJ5G51N0JWQC7XQ0)의 5단 파이프라인에 CSR 파일을 붙일 때 정할 것은 "어느 단에서 읽고 쓰는가"다. 명세는 CSR 접근이 프로그램 순서로 일어나야 하고, CSR 쓰기의 효과는 바로 다음 명령어가 관찰할 수 있어야 하며, 앞선 명령어가 그 효과를 먼저 보면 안 된다고 한다(Zicsr의 "CSR Access Ordering"). 이 요구를 지키려면 CSR 쓰기를 앞선 명령어가 모두 예외 없이 끝난 뒤에 해야 한다. 앞선 `lw`가 페이지 폴트를 낼 수 있는데 이미 `mstatus`가 바뀌어 있으면 안 된다. 흔한 선택은 이렇다.

- **읽기와 쓰기를 MEM 또는 WB 단에서 한다.** 불법 명령어 검사는 ID에서 끝내 두고(2절 식), 쓰기는 뒤쪽 단에서 한다. 읽기를 MEM에서 하면 로드와 같은 해저드가 생긴다. 바로 다음 명령어가 읽은 값을 쓰면 값이 EX/MEM에 없으므로 한 사이클 멈추거나 MEM/WB에서 포워딩한다. 17편의 조건식 `RegWrite ∧ rd≠0 ∧ rd=rs`는 그대로 쓴다.
- **CSR 명령어는 파이프라인을 직렬화한다.** 쓰기 효과가 앞단의 동작에 영향을 주는 CSR이 있기 때문이다. `satp`는 명령어 페치와 로드·스토어의 주소 변환을 바꾸고, `mstatus`의 `MPRV`·`SUM`·`MXR`은 로드·스토어의 번역과 권한을 바꾸고, `mstatus.FS`는 FP 명령어의 불법 여부를 바꾼다. 이 CSR을 쓴 뒤에는 이미 페치·디코드된 뒤따르는 명령어를 버리고 CSR 명령어 다음 pc로 다시 가져와야 한다. `mscratch` 같은 CSR은 이런 처리가 필요 없으니, 안전하게 모든 CSR 쓰기에 적용하고 느려도 좋다고 하든, 목록을 만들어 줄이든 정하는 것이 설계다. 30·31편에서 `satp`와 `SFENCE.VMA`를, 27편에서 트랩과 파이프라인 플러시를 다룬다.
- **`minstret`은 WB에서 센다.** 퇴직하는 명령어 수만큼 더한다. 단일 발행이면 최대 1이다. 같은 사이클에 `csrw minstret`가 WB에 있으면 5절 식대로 쓰기가 증가를 이긴다. `mcycle`은 매 클록 오르고, 클록이 멈추는 `wfi` 같은 상황의 정의는 구현 환경의 몫이라고 비특권 명세 8장이 적었다.

모델의 "명령어당 1사이클" 가정이 이 구조에서 어떻게 달라지는지는 확인하지 않았다. 5단 파이프라인에서 `mcycle`의 값은 사이클 수이므로 CPI를 곱한 만큼 `minstret`와 벌어진다. 두 카운터를 이 글의 모델처럼 1:1로 오르게 만든 것은 QEMU의 icount 방식과 맞춘 가정이다.

## 7. 실습: 모델과 QEMU 대조

시나리오는 구간(모드, 명령어 목록)의 나열이다. 같은 목록으로 두 가지를 만든다. 하나는 QEMU용 어셈블리다. 명령어마다 값과 센티널을 `li`로 준비하고 CSR 명령어를 실행한 뒤 `a0`(읽은 값)과 마지막 트랩의 `mcause`를 기록한다. 트랩이 나면 `a0`이 센티널로 남아서 기록에서 구분된다. S·U모드는 23편의 `enter_mode`로 내려갔다 온다. 카운터 시험은 명령어 사이에 다른 명령어가 끼면 값이 달라지므로 값을 담을 레지스터를 미리 배정하고 창이 끝난 뒤에야 저장한다. 다른 하나는 모델에 먹이는 것이다. 모델 한 사이클의 핵심은 이렇다.

```python
def step(self, mode, ins=None, retire=True):
    ...
    try:
        self._check(mode, a, writes)              # 존재, 모드, [11:10], 추가 조건
        old = self._read(a)                       # 보기·그림자를 거친 읽은 값
        if writes:
            new = src if rw else old | src if rs else old & ~src
            self._write(a, new)                   # 보기 마스크, WARL 정리
    except Illegal:
        cause = 2; retire = False
    inh = st['mcountinhibit'] if self.order == 'before' else inh_old
    bump(0, 0, True); bump(2, 2, retire)          # 카운터 갱신
```

`order='after'`는 5절의 레지스터 식과 같다(증가를 쓰기가 대신하고, 억제 변경은 다음 명령어부터). `order='before'`는 쓰기를 먼저 반영한 뒤 그 명령어의 증가를 센다. 모델은 QEMU를 보고 맞춘 것이 아니라 명세로 먼저 만들었고, 어긋난 칸을 보고서야 `before`와 `carry='none'`을 넣었다.

| 구성 | 비교한 칸 | 명세 순서 모델 | QEMU 순서 모델 |
|---|---|---|---|
| RV64 | 349 | 330 일치, 19 불일치 | 349 일치 |
| RV32 | 351 | 320 일치, 31 불일치 | 351 일치 |

RV64의 349칸 중 187칸은 원인(트랩 여부)만, 162칸은 값까지 비교했다(실행마다 값이 다른 `cycle`·`time`·`mcycle` 읽기는 원인만). RV32는 187칸과 164칸이다. 불일치는 모두 카운터 창이다. RV64의 19칸은 `mcycle` 창 5, `minstret` 창 4, 억제 해제 3(`CY|IR`) + 4(CY만), `csrrs`로 고친 카운터 3칸이고, RV32의 12칸이 더 있는 것은 반쪽 읽기 시험에서 올림이 없는 QEMU와 올림이 있는 명세 모델이 갈린 칸이다. 같은 프로그램을 두 번 돌려 비교 칸의 값이 같은지도 확인했고(결정적), 시작 직후의 `cycle`·`time`·`mcycle` 읽기만 실행마다 달랐다.

재현은 `uv run python check.py`다(`results.json`을 만든다).

## 8. 설계 체크리스트: CSR 파일

| 항목 | 규칙 |
|---|---|
| 쓰기 시도 | 명령어 칸으로 정한다. `rw`는 항상, `rs`·`rc`는 `rs1`≠`x0`(`uimm`≠0)일 때. 값이 0이어도 `rs1`≠`x0`이면 쓰기 |
| 읽기 시도 | `csrrw`·`csrrwi`는 `rd`=`x0`이면 읽지 않는다. 읽기 부작용을 걸지 않는다 |
| 권한 검사 | 존재, 모드 ≥ `csr[9:8]`, 쓰기 시도 ∧ `csr[11:10]`=11이면 불법, CSR별 추가 조건 |
| 불법이면 | CSR을 바꾸지 않는다. 쓰기 허용 신호를 검사 뒤에 건다 |
| 추가 조건 | 카운터는 `mcounteren`(S·U)과 `scounteren`(U)을 모두 통과, S모드 `satp`는 `TVM`, `fcsr` 계열은 `FS`≠Off |
| 보기 | 저장소 하나에 읽기·쓰기 마스크. 쓸 때 보인 값 위에서 계산. 따로 저장하지 않는다 |
| 파생 비트 | `SD`는 `FS`·`VS`·`XS`에서 읽을 때 만든다 |
| 읽기 경로 ≠ 쓰기 경로 | `mip.SEIP`는 읽을 때 외부 신호가 OR되고 `csrrs`·`csrrc`의 쓰기에는 소프트웨어 비트만 쓴다 |
| 다른 CSR을 바꾸는 쓰기 | `fflags`·`frm`·`fcsr` 쓰기는 `mstatus.FS`를 Dirty로. 쓰기 포트 병합 |
| WARL 정리 | 합법 값으로 만들거나 쓰기를 무시. 선택(MODE, `MPP`, `satp.MODE`)을 코드 한 곳에 드러낸다 |
| 구현 안 한 것 | 읽기 전용 0(`mie`·`mcounteren`·`mcountinhibit`의 없는 비트, 없는 `hpm`) 또는 불법 |
| 카운터 | 쓰기가 증가를 대신한다. 억제 변경은 다음 명령어부터. `minstret`은 쓰는 명령어를 세지 않는다 |
| `mcountinhibit` | CY·IR·HPM만. `time`은 억제할 수 없다 |
| RV32 | 반쪽 읽기는 올림에 찢어진다. 64비트 카운터는 위 절반으로 올림 |
| 파이프라인 | 쓰기는 앞선 명령어가 끝난 뒤. `satp`·`MPRV` 같은 CSR 쓰기는 뒤 명령어를 플러시 |

## 정리

- CSR 파일은 디코드·검사·읽기 mux·쓰기값 계산·WARL 정리·저장소다. 쓰기 시도는 `rs1` 칸으로 정하고(`rs1`≠`x0`이면 값이 0이어도 읽기 전용 CSR은 불법), 보기는 마스크 두 개로 한 저장소를 가리킨다.
- 사이클 단위 모델과 QEMU의 대조에서 권한 행렬, `sstatus`·`sie`·`sip` 보기, `stvec`·`MPP`·`satp` 정리, `fflags`의 `FS` 갱신이 모두 맞았다. RV64 349칸과 RV32 351칸 중 어긋난 것은 카운터 창뿐이었다.
- 카운터는 "쓰기가 증가를 대신하고 억제 변경은 다음 명령어부터"가 명세다. QEMU는 쓰기를 먼저 반영해 1씩 크게 읽었고 RV32 `mcycleh`가 올림을 받지 않았다. QEMU는 사이클 정확하지 않으니 카운터 값 대조에는 `-icount`가 필요하다.
- CSR을 파이프라인에 넣을 때는 쓰기를 뒤 단에서, 앞단 동작에 영향을 주는 CSR은 쓴 뒤 플러시한다. 불법 명령어의 실제 트랩 진입은 다음 글이다.

**다음 글:** 25편은 트랩이다. 예외와 인터럽트의 종류, `mtvec`의 직접·벡터 모드, 트랩을 받을 때 하드웨어가 `mepc`·`mcause`·`mtval`·`mstatus`를 어떻게 바꾸는지, `mret`가 되돌리는 것을 본다. 이 글의 불법 명령어가 어떻게 `mcause`=2로 기록되는지도 거기서 완성된다.
